# 문서 작성 규칙

이 문서는 저장소의 Markdown 문서를 같은 구조와 표현으로 쓰기 위한 규칙이다. 문장과 답변의 문체는 `CLAUDE.md` 11장을, 핸드오프 형식은 `CLAUDE.md` 10장을 따르며 여기에 다시 적지 않는다.

## 1. 공통 규칙

### 1.1 한 내용은 한 곳에만 쓴다

내용마다 기준 문서가 하나씩 있다. 다른 문서에서 그 내용이 필요하면 한 줄로 요약하고 출처(파일과 절)를 붙인다. 요약과 기준 문서가 다르면 기준 문서가 맞는 것으로 보고, 요약을 고친다.

- 연구 질문, 설계, 결정, 정의의 기준 문서는 `RESEARCH.md`이다.
- 작업 규칙과 확인된 명령의 기준 문서는 `CLAUDE.md`이다(명령은 6장).
- 환경, 버전, 실행 방법의 기준 문서는 `README.md`이다.
- 실험 설정, 결과, 관찰의 기준 문서는 `LAB_NOTEBOOK.md`이다.
- 현재 단계와 다음 작업의 기준 문서는 `STATUS.md`이다.
- 작업 단위의 경과와 맥락의 기준 문서는 `issues/NN-이름.md`이다.

### 1.2 표기

- 날짜는 `YYYY-MM-DD` 형식의 절대 날짜로 쓴다. "어제", "다음 주" 같은 상대 표현은 시간이 지나면 뜻이 바뀌므로 쓰지 않는다.
- 파일을 가리킬 때는 저장소 기준 상대 경로 Markdown 링크를 쓴다. 이슈 파일 안에서는 `../` 경로가 된다.
- 숫자에는 단위와 환경(맥북 로컬인지 Pi인지)을 붙이고, 결과 숫자에는 커밋 해시도 붙인다.
- 이슈는 `#3`처럼, 작업 단위는 `#3-1`처럼 번호로 부르고, 처음 언급할 때 파일 링크를 단다.
- 사람은 "연구자"라고 쓴다.

### 1.3 확인 상태

사실을 적을 때는 확인한 정도를 다음 표현 중 하나로 드러낸다. `RESEARCH.md` 10.1절이 쓰는 표현과 같다.

- 확인한 사실에는 출처(공식 문서 링크, 또는 로컬 확인의 날짜, 기기, 버전)를 붙인다.
- 문서에 직접 적혀 있지 않고 추론한 내용에는 "추론"이라고 쓴다.
- 확인하지 못한 내용에는 "확인 필요" 또는 "확인하지 못했다"라고 쓴다.

### 1.4 용어

- 처리 모델은 `platform`, `virtual`, `coroutine`(프로파일 이름)으로 부른다.
- 실험 변수는 `RESEARCH.md` 6.3의 이름(처리 모델, 풀 크기, 쿼리 유형, JDK, IO 병렬도, 도착률)을 그대로 쓴다.
- 도착률의 단위는 "건/초"이고, 처리량의 단위는 "req/s"이다.

## 2. 이슈 파일 (`issues/NN-이름.md`)

### 2.1 원칙

새 세션이 이슈 파일 하나만 읽고도 작업을 이어갈 수 있어야 한다. 그래서 작업에 필요한 결정, 제약, 관련 파일, 열린 질문을 이슈 안에 요약해 둔다. 요약은 1.1을 따라 한 줄씩 쓰고 출처를 붙인다. 긴 설명은 옮겨 적지 않고 출처로 보낸다.

### 2.2 파일 이름과 상태

- 파일 이름은 `두 자리 번호-영문 소문자 이름.md`이다(예: `03-local-compose-k6.md`). 번호는 만든 순서이며, 다시 쓰지 않는다.
- 상태는 `대기`, `진행 중`, `보류`, `완료 (YYYY-MM-DD)` 중 하나이다.
- 파일은 지우지 않는다. 필요 없어진 이슈는 `보류`로 두고 이유를 핸드오프에 쓴다.

### 2.3 작업 단위

이슈는 작업 단위 여러 개로 나누고, 한 채팅에서는 단위 하나만 수행한다(`CLAUDE.md` 10장). 단위는 파일 수가 아니라 독립적으로 확인되는 동작 하나로 자른다. 파일 수로 자르면 동작이 깨진 중간 커밋이 생기고(예: Compose에 앱만 있고 DB가 없어 기동은 되지만 `/query`가 모두 실패하는 상태), 계획에 있던 내용을 단위마다 다시 승인하는 왕복이 생기기 때문이다.

**단위의 정의.** 단위 하나는 아래를 모두 만족한다.

- 목표 동작을 "X하면 Y가 된다"는 한 문장으로 쓸 수 있다. 문장에 "그리고"가 들어가면 두 단위인지 다시 본다.
- 그 동작을 확인하는 근거가 있다. 근거는 영역마다 다르다.
  - `app/` 코드는 자동 테스트로 확인한다. 버그 수정과 기능 추가는 수정 전에 실패하고 수정 후에 통과하는 테스트를 근거로 한다. 동작을 바꾸지 않는 리팩터링은 기존 테스트가 바뀌지 않은 채 통과하고 `/actuator/info`의 설정 값이 같다는 것을 근거로 한다.
  - `infra/`, `load/`, 실행 스크립트는 확인 명령과 기대 결과를 이슈에 적고, 실제 출력의 요약을 핸드오프에 남긴다(예: 시드 행 수가 10000이다).
  - `analysis/`는 같은 원자료로 다시 실행하면 같은 결과가 나오는 것을 근거로 한다.
  - 연구자의 결정만으로 이루어진 단위는 결정과 근거가 기준 문서에 기록된 것을 근거로 한다.
- 단위가 끝난 커밋은 정상 상태이다. 테스트와 확인 명령이 통과하고, 기록된 명령을 그대로 따라 하면 동작한다. 실험 장치가 반만 바뀐 상태(예: 실행 스크립트는 새 CSV 열을 쓰는데 분석 스크립트는 옛 열을 읽는 상태)로 커밋하지 않는다.

**반드시 나누는 경우.** 하나라도 해당하면 다른 단위로 나눈다.

1. 변경 성격이 다르다. 동작 변경, 동작을 바꾸지 않는 리팩터링, 단위와 무관한 문서 정리는 섞지 않는다. 섞으면 실험 결과가 바뀐 원인을 커밋으로 구분할 수 없다. 단위의 결과를 기록하는 문서 갱신(`README.md`, `CLAUDE.md` 6장의 명령, 이슈의 핸드오프, `STATUS.md`)은 섞는 것이 아니라 그 단위에 포함한다.
2. 결정 의존이 다르다. 연구자의 결정이 필요한 변경과 필요 없는 변경을 나눈다. 결정을 기다리는 동안 다른 변경이 막히지 않게 하려는 것이다.
3. 영역이 다르다. `app/`, `infra/`, `load/`, 실행 스크립트, `analysis/`는 깨질 수 있는 범위가 서로 달라서 나눈다.
4. 실행 환경이 다르다. 같은 영역이라도 맥북 로컬과 Pi처럼 확인하는 환경이 다르면 나눈다. Pi에서 하는 단위는 명령을 실행하기 전에 연구자에게 알려야 한다(`CLAUDE.md` 6장).
5. 실험 조건이 바뀐다. 공통 코드(레포지토리, 쿼리), 기본 설정값, DB 스키마와 시드, 결과 CSV의 열 구성, `RESEARCH.md` 6.6의 정의를 바꾸는 변경은 그것을 처음 쓰는 동작과 함께 하되 다른 변경과 섞지 않는다. 이 커밋을 경계로 이전 결과와 비교할 수 있는지가 갈리기 때문이다.
6. 측정 실행이다. 측정 실행과 결과 기록(`exp` 커밋)은 코드 변경과 다른 단위로 둔다. 실행 전에 모든 변경이 커밋되어 있어야 하기 때문이다(`CLAUDE.md` 3장).

**나누면 안 되는 경우.**

- 새 코드와 그 코드의 첫 호출자. 예를 들어 Compose 서비스와 그것을 기동하는 기록된 명령, 결과 CSV의 새 열과 그 열을 채우는 수집 코드는 한 단위에서 만든다. 호출자가 없는 코드만 담긴 커밋을 만들지 않는다.
- 동작과 그 동작의 확인 근거. 테스트나 확인 명령을 다음 단위로 미루지 않는다.
- 변경 때문에 깨지는 기존 테스트, 문서, 명령의 수정. 원인이 된 변경과 같은 단위에 넣는다.

**표기.** 단위는 `#3-1`처럼 이슈 번호와 순번으로 부른다. 순번은 다시 쓰지 않으며, 진행 중에 단위를 나누면 새 순번을 붙이고 원래 단위에는 `(→ #3-5, #3-6으로 나눔)`이라고 쓴다. 단위의 상태는 `대기`, `진행 중`, `완료 (YYYY-MM-DD, 커밋 해시)` 중 하나이다. 커밋 메시지에는 단위 번호를 쓰지 않는다(`CLAUDE.md` 7장).

### 2.4 절 구성

모든 이슈는 아래 순서로 절을 둔다. 내용이 없는 절은 "없음"이라고 쓰고 절을 지우지 않는다.

```markdown
# #N 제목

- 상태: 대기
- 선행: #M (상태)
- 후행: #K
- 최종 갱신: YYYY-MM-DD

## 목표

왜 이 작업이 필요한지와 무엇을 만드는지를 두세 문장으로 쓴다.

## 완료 기준

- 끝났는지 확인할 수 있는 문장으로 쓴다.

## 작업 맥락

### 이미 정해진 것
- 이 이슈 밖에서 정해진 결정과 확인된 사실을 한 줄로 쓰고 출처를 붙인다. (`RESEARCH.md` 6.1)

### 지켜야 할 규칙
- 이 이슈에서 특히 어기기 쉬운 규칙만 출처와 함께 쓴다. (`CLAUDE.md` 3장)

### 관련 파일과 명령
- [경로](../경로): 이 이슈와 관련된 역할을 한 줄로 쓴다.
- 아직 없는 파일은 "만들 예정"이라고 쓴다.

## 열린 질문

- Q1. 연구자가 정해야 하는 것을 질문으로 쓰고, 알려진 선택지와 근거, 이 질문을 기다리는 단위를 붙인다.

## 결정 기록

- YYYY-MM-DD Q1. 질문 → 결정. 이유. 기록 위치: `RESEARCH.md` 6.1

## 작업 단위

### #N-1 제목
- 상태: 대기
- 동작: X하면 Y가 된다.
- 확인 방법: 테스트 이름이나 확인 명령과 기대 결과
- 필요한 결정: Q1 (또는 없음)
- 할 일:
  - [ ] 항목

## 결과

완료할 때만 쓴다. 산출물, 마지막 커밋, 다른 문서로 승격한 결정의 위치, 다른 이슈로 넘긴 일을 쓴다.

## 핸드오프

### 핸드오프 (YYYY-MM-DD, #N-1)
...
```

### 2.5 절별 규칙

- **머리말**: 선행 이슈의 상태를 함께 쓴다. 다른 곳에서 옮겨 온 이슈는 `- 출처:` 줄을 더한다.
- **완료 기준**: "만든다" 같은 행동이 아니라 "명령 하나로 기동하고 종료할 수 있다"처럼 확인할 수 있는 상태로 쓴다.
- **이미 정해진 것**: 이 이슈 밖(`RESEARCH.md`, 다른 이슈)에서 정해진 것과 확인된 사실만 쓴다. 이 이슈 안에서 내린 결정은 결정 기록에 쓰고 여기에 다시 쓰지 않는다.
- **지켜야 할 규칙**: `CLAUDE.md`를 복사하지 않는다. 이 이슈에서 실수하기 쉬운 규칙 몇 개만 고른다.
- **열린 질문**: 질문마다 `Q1`처럼 번호를 붙이고, 번호는 다시 쓰지 않는다. 결정되면 질문을 지우고 결정 기록으로 옮긴다.
- **결정 기록**: 이 이슈에서 연구자가 내린 결정을 날짜순으로 누적한다. 질문, 결정, 이유, 기록 위치를 한 줄에 쓴다. 설계에 해당하는 결정은 `RESEARCH.md`에도 쓰고 그 위치를 적는다. 결정을 뒤집을 때는 앞 줄을 고치지 않고 새 줄을 더한다.
- **작업 단위**: 2.3을 따른다. 다른 이슈로 넘긴 할 일은 지우지 않고 `(→ #N)`을 붙여 체크한다.
- **결과**: 작업 맥락과 겹치는 설명은 쓰지 않는다.
- **핸드오프**: 파일 끝에 누적만 한다. 제목에 날짜와 단위 번호를 쓴다. 앞의 핸드오프가 틀렸으면 고치지 않고, 새 핸드오프에 바로잡는 내용을 쓴다. 가장 마지막 핸드오프가 현재 상태이다.

### 2.6 이슈의 생애

1. 이슈의 첫 단위를 시작할 때 상태를 `진행 중`으로 바꾼다.
2. 단위를 시작할 때 그 단위가 기다리는 열린 질문부터 연구자에게 묻고, 답을 결정 기록에 쓴다.
3. 단위를 마칠 때 단위 상태, 핸드오프, 머리말의 최종 갱신일을 고친다. 단위를 진행하다가 더 나눠야 한다는 것을 알게 되면 2.3의 표기대로 나눈다.
4. `RESEARCH.md`의 결정이 바뀌면, 그 결정을 요약해 둔 `대기`와 `진행 중` 이슈의 작업 맥락도 같은 세션에서 고친다.
5. 마지막 단위가 끝나면 결과 절을 쓰고, 앞으로도 유효한 결정과 교훈을 `RESEARCH.md`로 승격한 뒤 상태를 `완료 (날짜)`로 바꾼다(`CLAUDE.md` 10장).

## 3. STATUS.md

- 덮어쓰기 전용이며 약 60줄 이내로 유지한다(`CLAUDE.md` 10장).
- 절은 프로젝트, 지금 단계, 바로 다음 채팅에서 할 일, 열린 항목, 일정, 읽는 순서의 순서로 둔다.
- 저장소 상태에는 최신 커밋 해시, 푸시 여부, 미커밋 작업 유무를 쓴다.
- "바로 다음 채팅에서 할 일"은 작업 단위 하나(`#3-1` 등)만 가리킨다(`CLAUDE.md` 10장).
- "새 채팅에서 입력할 프롬프트"는 그대로 붙여 넣을 수 있는 한 문장으로 쓰고, 읽을 파일을 경로로 적는다.
- 이슈에 이미 있는 맥락은 다시 쓰지 않고 이슈 파일로 보낸다.

## 4. RESEARCH.md

- 결정을 기록할 때는 `**결정**:`을 앞에 두고, 날짜와 결정한 사람(연구자)을 쓴다. 문서와 다른 점에서 나온 결정은 `D1`처럼 번호를 붙인다.
- 문서를 고치면 14장 변경 이력에 한 줄을 추가한다. 형식은 `- vX.Y.Z (YYYY-MM-DD): 바뀐 절과 내용`이다.
  - 설계, 결정, 정의가 바뀌면 둘째 자리를 올린다(예: v0.4 → v0.5).
  - 확인 결과의 추가나 문구 정리처럼 설계가 그대로이면 셋째 자리를 올린다(예: v0.4 → v0.4.1).
  - 6.6의 정의와 임계값은 연구자의 승인 없이 바꾸지 않는다. 바꾸면 이력에 이유를 쓴다(`CLAUDE.md` 2장).
- 확인 결과는 10.1절에 쓰고, 1.3의 확인 상태 표현을 지킨다.

## 6. README.md

- 절은 고정 버전, 빌드와 실행, 인프라, 부하 실행, 결과와 분석의 순서로 둔다. 아직 없는 절은 만들지 않는다.
