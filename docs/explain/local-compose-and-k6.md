# 로컬 Compose와 k6 해설 (#3)

앱, PostgreSQL, 부하 생성기를 명령 한 줄로 띄우고 같은 조건으로 부하를 거는 부분입니다. 명령의 기준은 [AGENTS.md](../../AGENTS.md) 6장과 [README.md](../../README.md)이고, 이 문서는 각 파일이 왜 그렇게 생겼는지를 설명합니다.

## 1. 큰 그림

- [infra/compose.yaml](../../infra/compose.yaml)은 DB와 앱을 한 번에 띄웁니다. 맥북과 Pi가 함께 쓰는 기본 파일이고, Pi에서는 [compose.pi.yaml](../../infra/compose.pi.yaml)이 일부를 덮어씁니다(1~2행 주석).
- [app/Dockerfile](../../app/Dockerfile)은 앱 이미지를 만듭니다. 이미지는 JDK 21과 25 두 가지로 만들며, 둘의 차이는 실행 JRE뿐입니다.
- [infra/db/init.sql](../../infra/db/init.sql)은 시드 데이터를 만듭니다.
- [load/e1.js](../../load/e1.js)는 k6 스크립트입니다. 고정된 도착률로 요청을 보내 지연을 잽니다.
- [load/install-k6.sh](../../load/install-k6.sh)는 k6를 버전과 해시로 고정해 설치합니다.

## 2. compose.yaml: DB 서비스

- **이미지 고정(8행)**: 태그와 digest를 함께 적었습니다. 태그는 같은 이름으로 다시 빌드될 수 있어서, 내용까지 고정하려면 digest(`@sha256:...`)가 필요합니다. 이 digest는 여러 CPU 구조를 묶은 목록을 가리키므로 맥북(arm64)과 Pi(arm64) 모두 같은 이미지를 받습니다.
- **설정은 이미지 기본값(9행)**: `command`로 PostgreSQL 설정을 넘기지 않습니다. 설정을 바꾸면 실험 대상이 바뀌므로 `AGENTS.md` 2장의 "변수 외 고정"을 지키는 것입니다.
- **계정(10~14행)**: LAN 안에서만 쓰는 실험용 계정이라 단순한 값을 씁니다.
- **시드(17~19행)**: `init.sql`을 컨테이너의 `/docker-entrypoint-initdb.d`에 읽기 전용으로 연결합니다. 이 폴더의 스크립트는 **데이터 디렉터리가 비어 있을 때만** 실행되므로, 시드를 다시 만들려면 `down -v`로 볼륨까지 지워야 합니다(18행 주석).
- **healthcheck(20~25행)**: `pg_isready`가 성공해야 "건강"으로 판정합니다. 기동 중 임시 서버는 소켓만 열어서 `-h 127.0.0.1`로 TCP를 확인합니다(21행). 덕분에 `up --wait`가 시드 적재가 끝난 뒤에 돌아옵니다.

## 3. compose.yaml: app 서비스

- **빌드(28~32행)**: `../app`을 컨텍스트로 빌드하고, `JDK`를 빌드 인자로 넘깁니다. 값 없이 이름만 적으면 셸에 있을 때만 전달되고, 없으면 Dockerfile의 `FROM`이 실패합니다(31행 주석).
- **환경변수(33~42행)**: `SPRING_PROFILES_ACTIVE`, `POOL_SIZE`, `IO_PARALLELISM`은 값 없이 이름만 적었습니다. 이렇게 하면 셸에 값이 없을 때 컨테이너에도 설정되지 않아, 앱이 기동 단계에서 실패합니다. 빈 문자열이 들어가 기본값으로 뜨는 사고를 막으려는 것입니다(34~35행). 접속 정보는 실험 변수가 아니라서 값을 고정합니다(39~42행).
- **포트(43~44행)**: 호스트 8080을 컨테이너 8080에 연결합니다.
- **기동 순서(45~47행)**: DB가 healthy가 된 뒤에 앱이 뜹니다. 시드 적재가 끝나기 전에 앱이 요청을 받는 일을 막습니다.

## 4. Dockerfile: 같은 앱, 다른 JDK

- 6행의 `ARG JDK`는 첫 `FROM`보다 앞에 있어야 합니다. `FROM`에서 쓰는 인자이기 때문입니다. 기본값이 없어서 빠뜨리면 빌드가 실패합니다(5행 주석).
- 7~8행은 JDK 21과 25의 JRE 이미지를 각각 이름 붙인 단계로 선언하고, 10행의 `FROM jre${JDK}`가 그중 하나를 고릅니다. 두 이미지 모두 Ubuntu 24.04(noble) 기반이라 OS가 JDK 비교의 변수가 되지 않습니다(3행).
- 12행은 호스트에서 만든 jar를 복사합니다. `./gradlew test bootJar`로 테스트를 거친 jar를 그대로 쓰기 위해서입니다(2행).
- 15행의 `ENTRYPOINT`에는 JVM 옵션이 없습니다. 힙 크기 같은 옵션을 주면 JVM 설정이 변수가 되므로 기본값으로 고정하고, 실제 값은 `/actuator/info`로 기록합니다(14행).
- 이 이미지는 맥북에서 만든 것을 Pi로 옮겨 쓸 계획입니다. 맥북이 arm64라서 Pi와 CPU 구조가 같습니다(RESEARCH.md 6.1).

## 5. init.sql: 데이터를 어떻게 만들었나

- 1만 행에 행당 100바이트라 전체가 약 1MB입니다. DB 메모리에 모두 올라가서 디스크 I/O가 측정에서 빠집니다(2행). 풀 크기 공식의 "디스크를 기다리는 시간이 없다"는 조건에 대응합니다.
- 11행의 `rpad(md5(g::text), 100, 'x')`는 id로부터 값을 결정적으로 만듭니다. 실행마다 데이터가 똑같아집니다(3행).
- 13행의 `ANALYZE`는 통계를 갱신해 쿼리 계획이 일정하게 나오게 합니다.

## 6. e1.js: 열린 모델 부하

### 열린 모델이란

요청의 도착 간격이 서버의 응답과 무관하게 정해지는 방식입니다. 서버가 느려져도 클라이언트는 같은 속도로 요청을 계속 보냅니다. 닫힌 모델은 응답을 받은 뒤에 다음 요청을 보내서, 서버가 느려지면 부하가 스스로 줄어 병목이 가려집니다. 이 연구는 풀이 포화되는 지점을 보려는 것이라 주 실험을 열린 모델로 합니다(`AGENTS.md` 3장).

### 시나리오 세 개 (45~76행)

- `ping_pre`: 부하를 걸기 전에 `/ping`만 보내 기준선을 잽니다.
- `query`: `/query`를 `constant-arrival-rate`로 보냅니다. 이 실행기가 열린 모델입니다.
- `ping_load`: 부하 중에도 `/ping`을 같은 속도로 보냅니다. 부하 전후의 `/ping`을 비교하면 네트워크와 Tomcat 몫이 변했는지 알 수 있습니다.

### 인자를 엄격하게 받는 이유

- 11~15행의 `required`는 값이 없으면 즉시 예외를 냅니다. 기본값을 두지 않아서 실행 스크립트가 값을 빠뜨리면 엉뚱한 설정으로 측정되는 대신 시작 단계에서 멈춥니다(2행).
- 17~21행의 `positiveInt`는 양의 정수만 받습니다.

### VU 수 계산 (43행)

- VU는 k6가 요청을 동시에 처리하는 가상 사용자 한 명입니다. 열린 모델에서 응답이 느려지면 더 많은 VU가 필요합니다.
- `/ping`의 VU 수는 `pingRate × (타임아웃 + 1초)`입니다. 부하 중 `/ping`이 느려져도 VU가 모자라 요청이 버려지지(dropped) 않게 해서, 지연 증가와 드롭이 섞이지 않게 합니다. 타임아웃된 반복이 타임아웃보다 조금 더 걸려서 딱 맞추면 드롭이 났기 때문에 1초분을 더했습니다(40~42행).

### 재현 가능한 id (99~109행)

- 요청의 id는 `(시드, 반복 번호)`만으로 정합니다. 어느 VU가 맡든 k번째 요청의 id가 같아서 실행을 다시 해도 요청 순서가 같습니다.
- 정수 해시(lowbias32)를 쓰는 이유는 난수 생성기의 상태에 의존하지 않고 순수 함수로 만들기 위해서입니다.

### 결과 기록 (128~143행)

- `handleSummary`는 받은 설정과 k6가 집계한 지표 전체를 JSON으로 그대로 저장합니다. 가공은 분석 스크립트가 원자료를 읽어서 합니다(128행 주석).
- `thresholds`(81~86행)는 판정용이 아닙니다. `dropped_iterations`와 타임아웃이 0일 때도 요약에 0으로 남게 하려고 항상 통과하는 조건을 걸었습니다.
- 지연은 `http_req_duration`입니다. 송신, 대기, 수신을 합한 값이며, 대기에 Tomcat 큐와 풀 대기가 들어갑니다(89행).

## 7. install-k6.sh: 왜 brew를 안 쓰나

- brew는 버전을 고정할 수 없고, 컨테이너로 돌리면 Docker VM의 NAT와 자원 제한이 지연과 VU 수에 끼어듭니다(3~4행). 그래서 공식 바이너리를 직접 받습니다.
- 8행의 SHA-256으로 받은 파일을 검증하고(21행), 맞지 않으면 설치가 중단됩니다. `set -euo pipefail`(5행)은 오류, 미정의 변수, 파이프 실패에서 즉시 멈추게 합니다.
- 설치 위치는 `load/.bin/k6`입니다. 이 경로는 gitignore 대상이라 저장소에 올라가지 않습니다.
