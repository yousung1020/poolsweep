# Pi용 Compose와 배포 흐름 해설 (#4-1)

[infra/compose.pi.yaml](../../infra/compose.pi.yaml)은 Pi에서만 쓰는 덮어쓰기 파일입니다. Pi 위에서 실행한 명령 자체는 [Pi 설정 명령 해설](pi-setup-commands.md)에 있고, 이 문서는 Compose 파일과 앞으로의 배포 흐름을 설명합니다. 결정의 기록은 [issues/04-pi-deploy.md](../../issues/04-pi-deploy.md)에 있습니다.

## 1. 큰 그림

- 로컬 맥북에서 쓰는 [compose.yaml](../../infra/compose.yaml)을 Pi에서도 그대로 쓰되, Pi에 맞지 않는 부분만 `compose.pi.yaml`이 바꿉니다. 이렇게 하면 DB 정의를 한 곳에 두어, 로컬에서 확인한 설정이 Pi에서도 똑같이 쓰입니다(compose.yaml 2행).
- 바뀌는 것은 세 가지입니다. 앱 이미지를 어디서 가져오는지, 포트, 메모리 제한입니다. 앱 설정값과 쿼리, DB 설정은 그대로입니다.
- 두 파일을 함께 쓰는 명령은 이렇게 생겼습니다(compose.pi.yaml 2행).

```
sudo env APP_IMAGE=... SPRING_PROFILES_ACTIVE=... POOL_SIZE=... docker compose -f compose.yaml -f compose.pi.yaml up -d --wait
```

- `-f`를 두 번 쓰면 뒤 파일이 앞 파일 위에 겹쳐집니다.
- `sudo env VAR=값 ...`을 쓰는 이유는 `sudo`가 환경변수를 그대로 넘겨주지 않을 수 있기 때문입니다. `env`로 값을 명시하면 확실히 전달됩니다.

## 2. 겹쳐 쓸 때의 규칙

Compose는 두 파일을 합칠 때 항목을 이렇게 처리합니다.

- 단일 값(`image`, `mem_limit`)은 뒤 파일의 값이 이깁니다.
- 목록(`ports`)은 **합쳐집니다**. 그대로 두면 앞 파일의 `8080:8080`과 뒤 파일의 `9080:8080`이 둘 다 열립니다.
- 그래서 목록을 통째로 바꾸거나 지울 때 특별한 표시를 씁니다. `!override`는 앞 파일의 값을 버리고 이 값으로 바꾸고, `!reset`은 값을 비웁니다.

맥북에서 `docker compose config`로 병합 결과를 확인했습니다. 앱 포트는 `9080→8080` 하나만 남았고, DB 포트는 없었으며, `APP_IMAGE`를 빠뜨리면 실패했습니다.

## 3. 파일을 줄별로 읽기

### db 서비스 (5~12행)

- 9행의 `ports: !reset []`는 기본 파일의 `5432:5432`를 지웁니다. 앱은 Compose가 만든 내부 네트워크에서 `db:5432`로 접속하므로 바깥에 열 이유가 없고, 기본 계정이 약한 DB를 LAN에 노출하지 않기 위해서입니다(6~7행).
- 12행의 `mem_limit: 1536m`은 DB 컨테이너가 쓸 수 있는 메모리를 1.5GB로 제한하려는 값입니다. 4GB 중 OS에 약 1GB를 남기는 대칭 값입니다(RESEARCH.md 6.2).

### app 서비스 (14~24행)

- 17행의 `build: !reset null`은 기본 파일의 `build`를 지웁니다. Pi에는 앱 소스와 빌드 도구가 없기 때문입니다(15행). 지우지 않으면 이미지가 없을 때 존재하지 않는 경로를 빌드하려다 실패합니다.
- 18행은 맥북에서 만들어 옮긴 이미지를 가리킵니다. `${APP_IMAGE:?...}`는 값이 없으면 오류로 멈춥니다. `latest` 같은 모호한 태그가 쓰이는 일을 막고, 어느 커밋의 이미지인지 태그로 추적하려는 것입니다(16행).
- 21~22행은 호스트 9080을 컨테이너 8080에 연결합니다. 왼쪽이 Pi 바깥에서 접속하는 번호이고, 오른쪽이 컨테이너 안에서 앱이 듣는 번호입니다. Pi에서 8080을 쓸 수 없어서 바깥 번호만 바꿨기 때문에 앱 설정은 달라지지 않고, 세 프로파일이 같은 조건을 유지합니다(19~20행).
- 24행의 `mem_limit`도 같은 값입니다.

### 지금은 적용되지 않는 부분

Pi 커널은 memory cgroup을 끈 채로 부팅합니다. 이 때문에 `mem_limit`은 파일에 있어도 **실제로는 적용되지 않습니다**(10~11행). 재부팅 없이 메모리 제한 없이 배포만 확인하기로 한 결정은 이슈의 결정 기록과 [RESEARCH.md](../../RESEARCH.md) 6.2에 있습니다. 적용 방법은 열린 질문 Q5로 남아 있습니다.

## 4. 배포 흐름 (예정)

아직 Pi에서 실행하지 않은 부분입니다. 단계마다 구현 여부를 표시했습니다.

1. 맥북에서 앱을 빌드합니다. `./gradlew test bootJar`로 jar를 만듭니다. (구현됨)
2. 맥북에서 arm64 이미지를 JDK 21과 25로 빌드해 `poolsweep-app:<커밋 해시>-jdk<21|25>`로 태그합니다. (아직 실행하지 않음: 맥북의 Docker Desktop이 꺼져 있었습니다)
3. `docker save`로 이미지를 파일로 묶고 SSH로 Pi에 보냅니다. (미연결)
4. Pi에서 `docker load`로 이미지를 불러옵니다. (미연결)
5. `compose.yaml`, `compose.pi.yaml`, `db/init.sql`을 Pi로 보냅니다. (미연결)
6. 위 1장의 `docker compose ... up -d --wait`로 기동합니다. (미연결)
7. 맥북에서 `http://<Pi 주소>:9080`의 `/ping`, `/query`, `/actuator/info`를 확인합니다. (미연결)

- **왜 파일 전송인가**: 레지스트리를 쓰려면 외부 서비스와 계정이 새로 필요합니다. 파일 전송은 의존성이 없고, 맥북에서 검증한 이미지를 그대로 옮길 수 있습니다.
- **왜 맥북에서 빌드하는가**: 맥북이 이미 arm64이고 빌드가 로컬에서 검증되어 있으며, Pi에 빌드 부하와 도구를 더하지 않아 측정 환경이 덜 바뀝니다(RESEARCH.md 6.1).
- **`availableProcessors`**: 7단계에서 이 값은 기록만 합니다. 코어를 나누기 전이라 4가 나올 것으로 예상하며, 2가 되는 것은 #4-2에서 확인합니다.

## 5. 이번에 한 문서 작업의 규칙

이 저장소는 작업을 이슈 파일과 `STATUS.md`로 이어 갑니다. 이번에 따른 규칙은 이렇습니다.

- 연구자가 내린 결정은 이슈 파일의 "결정 기록"에 날짜와 함께 누적하고, 설계에 해당하는 결정은 `RESEARCH.md`에도 적습니다. 결정을 뒤집을 때는 앞 줄을 고치지 않고 새 줄을 더합니다(`docs/WRITING.md` 2.5). 메모리 cgroup 건이 그 예입니다. 처음에 재부팅을 승인했다가 번복한 사실을 둘 다 남겼습니다.
- 세션을 마칠 때는 이슈의 "핸드오프" 끝에 한 일과 남은 일을 누적하고, `STATUS.md`는 덮어씁니다(`AGENTS.md` 10장). 다음 세션이 이 두 파일만 읽고 이어 갈 수 있게 하려는 것입니다.
- `RESEARCH.md`는 설계가 바뀌면 버전을 올립니다(이번에 v0.11에서 v0.12).
